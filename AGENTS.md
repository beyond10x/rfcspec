# AGENTS.md — rfcspec

The contract for changing this repository. Humans start at [`README.md`](README.md); the design is
[`docs/design/rfcspec.md`](docs/design/rfcspec.md).

## Serves

- **O2 — decisions as data, with evidence.** An RFC becomes a cited requirement catalogue, ESS
  documents for its machines and types, and a wire-format sidecar for its bytes and bits; a
  conformance matrix gives every requirement a status backed by tests.
- **O4 — products run on the foundation.** The generated protocol cores become native libraries
  and Spindle ports, so a product's specification names an exchange, not a protocol.

## State

The pipeline runs every stage end to end: S0–S2 and S4–S7 for three profiles, `profiles/time`
(RFC 868), `profiles/websocket` (RFC 6455 sections 5.2, 5.4, 5.5, 5.6 and 7) and `profiles/dns`
(RFC 1035 sections 4.1.1, 4.2.1 and 7.3), and S3 (AI proposals) for `profiles/websocket`. S3
records and replays proposals for five tasks, `status`, `requirement-from-prose`, `machine`,
`bit-widths` and `requirement-link`, and `rfcspec review` settles one with accept, edit or reject
into the overlay, adding a requirement entry, layout or machine. `profiles/websocket/proposals/`
holds the first recorded set: one `status` proposal for each catalogue requirement of RFC 6455
sections 5.1 and 5.3, recorded once from a model served on the local GPU, each decided in the
overlay (7 accepted or edited, 3 rejected with their reason), and replayed offline by the
`websocket` gate step `rfcspec propose --profile profiles/websocket --replay`. S2 also runs in
bulk, unreviewed, over every RFC the index publishes as plain text (`bulk/`); everything else is
design. What exists:

| path | what |
|---|---|
| `docs/design/rfcspec.md` | the design: decisions (§0), pipeline, catalogue, communication semantics, ESS gaps, WebSocket example, milestones (§14) |
| `ess/` | RFCspec's own ESS specification: the catalogue, profile (semantics, statuses, recorded runs) and review nouns |
| `examples/websocket/` | the WebSocket closing-handshake model (`ess-protospec/1`) and its exploration witness |
| `crates/rfcspec-{model,source,doc,extract,ess,gen,conformance}/` | the pipeline stages S0–S2 and S4–S7 (design §13) for plain-text RFCs |
| `crates/rfcspec-propose/` | S3: prompts for `status`, `requirement-from-prose`, `machine`, `bit-widths` and `requirement-link`, the `rfcspec-proposal/1` document (`<profile>/proposals/<proposal_id>.json`), mechanical checks, record through the `llm` crates (tag 0.20.0) and offline replay, skipping items the overlay has a decision on; and S4 over a recorded proposal (`review`): a decision (`decisions` in `rfcspec-overlay/1`, keyed by item and the SHA-256 of its whitespace-collapsed catalogue text) a reject holding its reason, and, for accept and edit, the requirement entry, inserted into the overlay without rewriting its other lines; its tests use an in-process model double |
| `crates/rfcspec-cli/` | the `rfcspec` binary: `fetch`, `read`, `extract`, `propose` (`--replay` offline), `review` (`--proposal <id>` then `accept`, `edit --entry <file>` or `reject --reason <text>`; writes the overlay only when its checks hold on the result), `check`, `lower`, `generate`, `verify`, and `bulk` (`fetch` into a cache outside the repository, `summarise` the cache, `check` a summary offline) |

| `profiles/websocket/` | RFC 6455: locked source, `profile.yaml` (one `tcp` layer, sections 5.2, 5.4, 5.5, 5.6 and 7 in scope), `overlay.yaml` giving every in-scope requirement a status (the rest of the catalogue counts as unreviewed, except the sections 5.1 and 5.3 requirements its review decisions accepted or edited), `proposals/` (the recorded `status` proposals of sections 5.1 and 5.3), the `close`, `ping` and `fragments` machines and their input witnesses, the `frame-header` layout, and `generated/` (`close.protospec.yaml`, `ping.protospec.yaml`, `fragments.protospec.yaml` and the `rfc6455-websocket` frame codec crate) |
| `profiles/dns/` | RFC 1035: locked source, `profile.yaml` (one `udp` layer correlated `by-id`, sections 4.1.1, 4.2.1 and 7.3 in scope), `overlay.yaml` (prose requirements only: RFC 1035 predates BCP 14), the `header` layout, the `query` machine (a response is accepted only when its ID equals the query's) and its input witness, and `generated/` (`query.protospec.yaml` and the `rfc1035-dns` header codec crate) |
| `crates/rfcspec-docs/` | generates the site's derived pages (design, status, and the protocol catalogue `website/docs/catalog/` with its downloads `website/static/downloads/`, both from `profiles/`) and binds a built site to its commit |
| `website/` | the Docusaurus site published at `https://beyond10x.github.io/rfcspec/`; `website/static/pitch/` is a standalone slide deck |
| `.engineering/` | the AEP planning store (`aep.project/5`) |

## Gate

```console
task check
```

Steps (`Taskfile.yml`): `aep plan artifact validate`, `ess specify validate --path ess`, bounded
exploration of every model under `examples/` must report `"verdict": "passed"`,
the `time` task (`rfcspec check --all profiles`, which also fails on a stale recorded run, an
in-scope requirement without a status, a recorded proposal that does not replay byte for byte, or
an overlay decision without its recorded proposal or judging another text than its item's current one,
`rfcspec lower --check`, exploration of both
Time Protocol models, `rfcspec generate --check`, `cargo test -p rfc868-time`),
the `websocket` task (`rfcspec propose --profile profiles/websocket --replay`,
`rfcspec lower --profile profiles/websocket --check`, exploration of the
`close`, `ping` and `fragments` models with their witnesses, `rfcspec generate --profile profiles/websocket --check`,
`cargo test -p rfc6455-websocket`),
the `dns` task (`rfcspec lower --profile profiles/dns --check`, exploration of the `query` model
with its witness, `rfcspec generate --profile profiles/dns --check`, `cargo test -p rfc1035-dns`),
the `bulk` task (`rfcspec bulk check --summary bulk/rfc-summary.jsonl --profiles profiles`, offline),
`rfcspec-docs generate --check`, `cargo fmt --check`, strict Clippy, `cargo test --workspace`.
CI (`.github/workflows/check.yml`) pins `ess` 0.86.0 and `aep` 0.79.0. The site build is separate:
`task website` (`npm ci --allow-git=root` locally; CI's Node 22 needs no flag).

## Release

A release `vX.Y.Z` is the `[workspace.package]` version in `Cargo.toml` set to `X.Y.Z`, merged to
`main` with `task check` green, then the tag `vX.Y.Z` on that merge commit and a GitHub Release
of the tag, both written through the bot (`POST /repos/beyond10x/rfcspec/git/refs`, then
`POST /repos/beyond10x/rfcspec/releases`). The release body lists what changed since the previous
tag. Nothing is published to a registry. The site deploys on every merge to `main`, independent
of releases.

## Rules

- Running code is Rust, clap derive for the command line. No Python, no shell helpers.
- Only the source crate (design §13, `rfcspec-source`) reaches the network, through two commands,
  `rfcspec fetch` and `rfcspec bulk fetch`; besides it only `rfcspec propose` recording through
  the `llm` crates does. Every other stage, and `rfcspec propose --replay`, reads
  locked sources and recordings and runs offline; no test or gate calls a model, reads a
  credential or reaches a website.
- `bulk/rfc-summary.jsonl` is regenerated only by `task bulk-regenerate` (`CACHE=<dir>` optional),
  never by hand; the commit names the index SHA-256, the row count and the time of the fetch. The
  cache it fetches into lies outside every Git working tree (`rfcspec bulk fetch` refuses one
  inside), and no RFC text, `rfc-index.xml` or cache file is committed. Model credentials are `llm.routes/1` references (`env:`,
  `file:`) the operator injects, never values in the repository.
- AI output is a recorded proposal with cited spans. It changes nothing until a review decision is
  written to a profile's overlay.
- ESS is read and written through its crates at a released tag; never re-implement ESS parsing or
  validation.
- Generated files are never edited by hand: change the generator in `crates/rfcspec-docs/`, then
  `task docs-generate`. The same holds for `profiles/*/generated/`: change the overlay or
  the generator, then `rfcspec lower` and `rfcspec generate`.
- A new noun gets its ESS declaration in `ess/` before any AEP story is written around it.
- No comments in `Cargo.toml`, `Taskfile.yml`, workflow files or YAML specifications.
- Confidentiality: this repository is public. No name of an external company, customer, product or
  host, and no `/home/<name>/` path, in any file or commit message. Text quoted verbatim from a
  published RFC or the RFC index (titles, authors, source lines) is exempt: it is public record.
- Builds: `CARGO_PROFILE_DEV_DEBUG=line-tables-only CARGO_INCREMENTAL=0`, the tree's own `target/`;
  check `df -h /` first.
- Commits and pushes are `b10x-bot[bot]` through `b10x-gates bot`; use managed worktrees for
  changes and keep the primary checkout clean.
