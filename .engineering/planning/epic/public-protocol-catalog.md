## Outcome

Timo, 2026-11-04: the public site keeps what it has today, the process from RFC to specification,
and gains a catalogue under one path of the docs, `/rfcspec/docs/catalog/`, as the index of every
protocol RFCspec has turned into a specification: WebSocket, SIP, the Time Protocol and many more.
"Having these specs basically means that we can auto-generate all kind of stuff, for everything."

## What the catalogue shows

- One index page listing every profile under `profiles/`: name, RFCs, kind (design §2.3), stage
  reached (S0–S7), requirement counts by level and by status, conformance verdict.
- One page per profile: its RFCs with links to rfc-editor.org, the communication semantics (§6),
  the requirement matrix, the ESS documents and generated artifacts as downloads, the ESS gaps it
  hit.
- Every page is generated by `rfcspec-docs` from the profile directories; `generate --check` in
  `task check` fails on drift. Nothing on it is hand-written.

## Depends on

The profile layout and the catalogue, overlay and lowering commands of
`epic:rfc868-thin-slice`; the Time Protocol is the first entry.

## Acceptance

On a clean checkout, `task check` exits 0 and `task website` builds, and the built site serves
`/rfcspec/docs/catalog/` (index with one row for `time`: RFC 868, kind K1, stage S6, 4 MUST and
2 SHOULD, 6 satisfied, conformance "no recorded run") and `/rfcspec/docs/catalog/time` (RFC 868
linked to rfc-editor.org, two semantics rows `tcp` and `udp`, six requirement rows, "no ESS gap",
four downloads byte-identical to `profiles/time/generated/`). Editing any generated catalogue
file by one byte makes `task check` exit 1.
