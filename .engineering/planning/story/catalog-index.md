## Story

`rfcspec-docs generate` reads every profile directory under `profiles/` and writes the protocol
catalogue index, `website/docs/catalog/index.md`, served at `/rfcspec/docs/catalog/`. It is the
first of five stories; it also turns the generator from a fixed list of outputs into one that
derives its outputs from `profiles/`, which the later stories extend.

## Acceptance

`task check` passes with a generated index that lists `time` with RFC 868, kind K1, stage S6,
4 MUST and 2 SHOULD requirements, 6 satisfied, and fails when the index is stale, edited or orphaned.

- `rfcspec-model` `Overlay` gains an optional `kind` (`K1` to `K8`, design section 2.3, the
  catalogue `RfcKind`); `profiles/time/overlay.yaml` declares `kind: K1`. An unknown value is a
  parse error. `rfcspec check --profile profiles/time`, `rfcspec lower --profile profiles/time
  --check` and `rfcspec generate --check` still pass with no change to `profiles/time/generated/`.
- The index is a table, one row per profile directory, sorted by name: name (plain text; `story:catalog-profile-page` adds the link to the page it creates), RFC numbers with titles from `profile.yaml`, kind
  (or `unclassified` when the overlay has none), stage reached, requirement counts by level and
  by status (`satisfied`, `unsupported`, `not-applicable`). No conformance verdict column
  (`decision-blocker:catalog-conformance-verdict`).
- Stage reached is the highest stage whose output is checked into the profile directory: S0
  `rfcspec.lock` with every locked source present at its SHA-256; S4 `overlay.yaml`; S5
  `generated/*.protospec.yaml`; S6 `generated/rust/Cargo.toml`. S1 to S3 store nothing in a
  profile and are never reported; S7 (a recorded run) is added by `story:catalog-recorded-runs`. For `profiles/time` this is S6. A unit test asserts
  each step on a fixture directory built up file by file.
- A unit test renders the index from `profiles/time` and a fixture profile under
  `crates/rfcspec-docs/tests/fixtures/profiles/` (one MUST `unsupported: ess-gap G1`, one SHOULD
  `not-applicable`, one MAY satisfied, no `kind`, no `generated/`) and asserts two rows in name
  order with the counts and stage (S4) of each. The fixture is read only by tests, never by
  `generate`.
- `rfcspec-docs generate --check` exits non-zero naming the file when the index is missing,
  stale or hand-edited, and when a Markdown file under `website/docs/catalog/` is not one it
  would generate (`unexpected website/docs/catalog/<file>`); `generate` deletes such a file. A
  unit test covers each case. The index passes `passive_check` (an RFC title with braces or a
  `<` stays passive through `page::cell`).
- `website/sidebars.ts` gains a `Protocol catalogue` category linking the generated index, with
  its items autogenerated from `catalog/`, so later profile pages need no sidebar edit;
  `website/docusaurus.config.ts` gains a navbar link to `/docs/catalog`. `task website` builds,
  and `rfcspec-docs provenance` on that build lists `/rfcspec/docs/catalog/` in
  `.well-known/b10x-routes.json`.

## Domain relations

- Catalogue index -> Profile, one-to-many, zero allowed; the index owns nothing and is a
  projection of the profile directories. Inferable (inferred from
  `crates/rfcspec-model/src/lib.rs:21`, `Profile`, and the layout `profiles/<name>/profile.yaml`;
  `ess/domains/profile.yaml` declares the view `rfcspec.profile.Profiles` but no catalogue noun).
- Profile -> Rfc, one-to-many, the profile references RFCs and owns none. Inferable (inferred
  from `ess/domains/profile.yaml`, type `rfcspec.profile.ProfileRfc`, a field typed
  `rfcspec.catalogue.RfcNumber` with no `relations:` entry, and `crates/rfcspec-model/src/lib.rs:29`).
- Rfc -> RfcKind, zero or one: `ess/domains/catalogue.yaml`, entity `rfcspec.catalogue.Rfc`,
  field `kind: Optional<rfcspec.catalogue.RfcKind>`. Kept in the overlay because design section
  2.3 makes the kind a reviewed S2/S3 result, and the overlay is the reviewed file of one RFC.
- Profile -> Status, one-to-many, the profile owns its statuses: `ess/domains/profile.yaml`,
  entity `rfcspec.profile.Profile`, relation `statuses`.
- Status -> Requirement, one: `ess/domains/profile.yaml`, entity `rfcspec.profile.Status`,
  relation `requirement`. Counts by level read the requirement; counts by status read its status.

## Scope

`crates/rfcspec-docs` (`main.rs` outputs keyed by path string, a new `catalog.rs`, tests and
`tests/fixtures/profiles/`), `crates/rfcspec-docs/Cargo.toml` (adds `rfcspec-model`),
`crates/rfcspec-model` (`Overlay.kind`), `profiles/time/overlay.yaml`, `website/docs/catalog/index.md`
(generated), `website/sidebars.ts`, `website/docusaurus.config.ts`, `Cargo.lock`. The task
`docs-check` already runs in `task check`; no `Taskfile.yml` change.

Label it `Protocol catalogue` everywhere: `website/docs/concepts/catalogue.md` already uses
"catalogue" for the per-RFC `rfcspec/1` requirement catalogue.
