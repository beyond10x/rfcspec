**Findings**

- story:explorer-rfc-view — the body never says where the shards' References come from. The sidecar holds per-section level counts only. `bulk summarise` gets only level counts from the reader, and `story:xref-reference-extract` changes `rfcspec read` and `Document` alone. Yet the acceptance has the 9220 shard carry the References `rfcspec read` gives, so the bulk path from `Document.references` to the shards is in neither item. Close it by having rfc-view say the sidecar rows carry each RFCXML RFC's References, or by adding `bulk summarise` to the xref story's scope. — `.engineering/planning/story/explorer-rfc-view.md:27`, `.engineering/planning/story/explorer-rfc-view.md:29`, `.engineering/planning/story/explorer-rfc-view.md:46`, `crates/rfcspec-cli/src/bulk.rs:21-29`
- story:explorer-rfc-view — the only type generation is `--target typescript`, so the Rust writer of the shards (`explorer.rs`) is hand-written and not tied to the ESS value types. The workspace rule is that types a browser shares with its server are generated and drift-checked. `uilab` generates both `--target rust` and `--target typescript` from one spec, and this story generates only the TypeScript half. Either generate the Rust types too or add a test that checks the written shards against the value types. — `.engineering/planning/story/explorer-rfc-view.md:30`, `uilab/Taskfile.yml:25-26`
- story:explorer-search — `rfc-index.json` rows carry the profile marks, which are not an `Rfc` field, and the scope names no ESS value type and no generated TypeScript for the row. The row shape would be hand-written twice, in Rust and in TS, with nothing to catch drift. Add the index-row type to `ess/domains/catalogue.yaml` and to the generated TS in the scope. — `.engineering/planning/story/explorer-search.md:20`, `.engineering/planning/story/explorer-search.md:30`, `.engineering/planning/story/explorer-search.md:39-43`

**The Vue-app-over-per-range-JSON decision** is sound against the workspace rules, so I raise no finding on the choice itself.
- The browser code is Vue 3, TypeScript, Vite and pnpm.
- The derivable data is generated by `rfcspec-docs` and drift-checked by `docs-check`, which is `generate --check` (`Taskfile.yml:110-114`).
- The Docusaurus site stays as it is, as in the 2026-10-04 exception.
- The query-string route (`?rfc=`) works on a static Pages host with one `index.html`.
- The 9,847 count matches the summary (9,848 lines including the header).
- `sidebars.ts:30` does autogenerate `catalog`, as the story says.
- The conclusion leans on one unmeasured figure, the build time of 9,847 pages, which the story itself discloses.
- The type-generation gap in the second finding is the only place the decision falls short of the rule.

**Shape of the set.** The edges are a tree, not a queue: xref-reference-extract, then explorer-rfc-view, then explorer-search and explorer-profile-layer, which are siblings. There is no cycle and no horizontal slice; rfc-view carries data, ESS types, shards and the UI end to end. No unrecorded dependency edge is missing.

**What you read:** five artifacts, using `show` on each, `relations`, `graph`, `validate` (valid, 129 artifacts), and the repo files `catalogue.yaml`, `bulk.rs`, `Taskfile.yml`, `pages.yml`, `sidebars.ts` and `uilab/Taskfile.yml`. I walked 10 edges touching the set: 4 `decomposes`, 3 `depends_on`, 2 `informed_by` and 1 `blocks`. All lead to artifacts inside the set or to the two informing epics, and I followed the `depends_on` edges outside the set (none) to confirm no cycle. I traced 5 acceptance reads to a producer in the set, and an edge records all 5. The first finding is a missing statement in the body, not a missing edge.

**What I could not establish:**
- Whether `bulk summarise` can reach `Document.references` cheaply. I only saw that it calls `rfcspec_doc::read_format`.
- The 9,847-page build time and the provenance step's behaviour with a Vite-hashed `website/build/explorer/`. The story's open questions already cover the unified-site carry-through.

**Out of my lane:**
- Parallel safety: explorer-search and explorer-profile-layer both edit `crates/rfcspec-docs/src/explorer.rs`, the `explorer/src` entry points and `explorer/src/generated/`.
- Acceptance: the profile-layer open question on "exploration witnesses", and `ess generate types --root <view>.row` omitting `--target` at `explorer-profile-layer.md:26`.
